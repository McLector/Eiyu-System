## Outcome and evidence

Recover readable Android layout after a live system-font change within Expo SDK54, while retaining unsaved work across both the system configuration change and any later explicit JS reload, recovery credentials in RAM, original-day queued actions and account isolation. Use the existing Auth, Settings, editor, mailbox and navigation flows. Collect no additional identity information. This is an acceptance target, not an established capability.

The [Oppo experiment](2026-10-20-s02-public-reload-font-spike.md) established that public `reloadAppAsync` reflows the retained SDK54 build: hot1.6 left sample height69 and clipped text; reload produced185 and all sample words. It also discarded an unsaved signup draft and returned a credential-free recovery route to login. These are historical observations on the retained scratch build, not final-candidate acceptance.

The exact [SDK54 reload source](https://github.com/expo/expo/blob/sdk-54/packages/expo-modules-core/src/reload.ts) promises the same bundle, not navigation or form preservation. The versioned Expo reference URL currently redirects to latest, so the [official SDK54 reference source](https://github.com/expo/expo/blob/sdk-54/docs/pages/versions/v54.0.0/sdk/expo.mdx) was used. The installed Router declarations expose public `replace`, `usePathname` and root navigation state; no hidden Router reload API is proposed. ## Approaches and recommendation

| Approach | Consequence |
| --- | --- |
| Automatically reload on font change or foreground | Rejected by the observed draft/route loss. A loading indicator or React Query mutation count does not cover all writers. |
| Explicit refresh at a verified safe point, with a local activity coordinator and durable queue checkpoint | Recommended. Adds integration work, but keeps secrets in RAM and makes refusal safer than losing work. |
| Persist and restore every form and navigation object across reload | Rejected for this scope. Would duplicate private free text and credentials, broaden storage/retention, and replay state that may belong to another account or expired callback. |

The recommended repair is deliberately deferred while work cannot safely be interrupted. It does not promise instant reflow during an active form or recovery attempt. No SDK upgrade, dependency patch, internal RN flag or font-scaling suppression is part of the repair.

### Prerequisite: activity continuity before the guard

Android can recreate an activity when the system font changes. Our retained quiet-release evidence already recorded a return from Weekly to Board before any app navigation. A JS coordinator cannot protect a form that the activity recreation has already discarded. Preventing a later explicit reload is insufficient.

The earlier disposable **public manifest `fontScale` configuration handling** retained the Activity/Weekly route, but did not repair text layout. That is a possible companion to the public reload primitive, not an internal RN feature flag and not a proved combined fix. Before any broad provider/queue/Auth integration, a separately reviewed minimal native/config-plugin experiment must establish exact SDK54 event forwarding, Activity identity, retained JS state and dirty form/recovery continuity through1.0→1.6→1.0. Preserve all existing configChanges values and forward configuration changes through the supported ReactActivity path. Do not add a speculative native override or revive the partial APK as an accepted repair.

If accepted, that public manifest change is a real native configuration change: it needs an appropriate runtime-version change, a new matching binary and generated/merged manifest verification. A JS-only update cannot supply it. The exact product integration and native change remain unapproved. Ordinary Android process death is separate: no promise is made to preserve passwords/callback credentials through process termination, and none may be persisted to make that promise.

The native prompt and the existing finish/cancel/check-result controls must also remain usable while reflow is deferred. If large text makes it impossible to finish or cancel an edit, the safe-refresh design is not an accessible repair merely because it avoids losing data. These are stop conditions for this approach, not reasons to collect/store secrets or suppress font scaling.

## User flow

Detect a finite positive font scale differing from the scale at this JS runtime's boot. Compare with a small numeric tolerance so1.6000000238 is not a distinct size from1.6. Track the newest scale, not a queue of changes. If the system returns to the boot scale, the layout may still be stale: the experiment demonstrated the reverse-direction defect. Keep refresh pending until a new runtime actually boots with the desired scale.

After the app returns active and Auth/bootstrap are known, show one native informational dialog per observed font-change revision. This avoids relying only on a Fabric notice whose own text may be clipped. Do not interrupt an existing native picker/permission dialog. A durable Settings entry, **Refresh text layout**, lets the user return after choosing Later. The Settings entry closes only its own sheet before presenting the native confirmation; other editors/sheets are not closed on the user's behalf.

When blocked, say: **“Font size changed. Finish or cancel your edits and let current saves finish before refreshing the layout.”** Offer **Later** only. For an unresolved save, say **“Check the save result before refreshing.”** Do not infer failure from a timeout or offer a blind resend.

When safe, say: **“Refresh text layout? Eiyu will briefly restart its view and return to this tab. Your saved data and queued actions will be kept.”** Offer **Later** and **Refresh layout**. This copy is conditional on successful implementation and physical acceptance of the queue/route contracts below. It is not an existing product promise.

No automatic refresh when a blocker later disappears. A fresh user press must recheck all conditions. This avoids an unexpected restart immediately after a save, verification or recovery completes. Normal quests remain usable while refresh is deferred. A blocked refresh never requires deleting a held action, signing out, proving identity or granting AI permission.

## Safe-point rules

Only stable top-level tabs or an entirely blank ordinary login screen may initiate refresh. Capture the tab just before commit. Editor/history/recovery routes, account overlays, native pickers, confirmation dialogs and active drags block it. An unopened background tab with unsaved Gym weights also blocks it; visible-route checks alone are insufficient.

| Surface | Required behavior |
| --- | --- |
| Signup, forgot-password, nonempty login | Block refresh. Mode, fields and unchecked choices stay in RAM. Return to blank login through the existing flow when finished; no silent discard or credential persistence. |
| Password recovery, including invalid-link/result screens | Block for the entire route and any pending native recovery transfer. Existing Back to sign in exits it. Never save a token, password or raw callback URL for layout recovery. |
| Quest/long-quest/Gym editors, profile, inline forms, Gym weight drafts | Block while open/dirty, pending, or uncertain. Existing save/discard/confirm-result controls determine when work is finished. A font action cannot invoke them automatically. |
| Mailbox verification | Block while a send/verify/check is active or a challenge/code draft remains. Add a small explicit **Cancel email verification** action in this existing panel, clearing only its RAM draft/challenge. It does not revoke existing proof, reset rate limits, change the mailbox or send mail. Finish or explicitly cancel before refreshing. Mere foregrounding does not cancel it. |
| Consent or birthday changes | Hold an operation lease through accepted result/invalidation; refresh cannot interrupt the mutation or reinterpret a checkbox as a server grant. Profile must be closed. |
| AI generation/regeneration and any request that can create/save a summary | Block until its actual promise/final persistence settles. Do not treat UI cancellation, unmount or a timeout as server completion. No extra generation/retry is requested for font refresh. |
| Ordinary writes outside React Query, media/cleanup, reminders, appearance and local persistence | Register their active lifetime. Durable cosmetic unsynced state can survive when its normal retry marker is confirmed stored; uncertain nonqueued data writes continue blocking until resolved through their existing flow. |
| Tracker queue | Preserve all entries, including offline/uncertain/failed/under12-held entries. Pause dispatch briefly and verify durable state; do not call `flush()` as a durability check. Active send/reconciliation blocks refresh. |

Do not rely on every form remembering to register only when it becomes dirty. Route/overlay presence conservatively blocks editor flows from mount; additional draft/operation registrations cover work retained off-screen. Missing participant readiness denies refresh.

## Coordinator and queue contract

Add a small mobile-only coordinator above the existing providers. It owns font-change state, participant readiness, nonsecret blocker categories, activity leases and a monotonic revision. It never receives field values, credentials, quest text or callback URLs. An operation acquires its lease synchronously before its first side effect and releases it only after the full result, dependent persistence and reconciliation bookkeeping settle. Rejected/unavailable admission performs no side effect. Every exit path releases once.

The post-dispatch latch belongs to the JS runtime, not only a mounted React provider. Strict Mode, provider remount or navigation unmount cannot clear it or release an operation whose actual promise remains active. No rejected admission may silently drop an enqueue/Retry/action behind optimistic UI: handlers must produce a typed refusal and leave the action/draft unchanged. Missing coverage of an existing writer denies refresh. An ambiguous nonqueued write with no existing receipt/result-check path remains an integration blocker; generic promise rejection or closing its screen does not establish a safe result.

Inventory and wire current operations explicitly: Auth sign-in/signup/sign-out/reset; Eiyu direct writes and reorder lanes; queue send/reconciliation; Gym/media/cleanup; appearance/reminder persistence; profile/birthday/consent; mailbox; AI read-or-create/regeneration; widget snapshot persistence. The widget headless handler currently reads a snapshot and draws it, with no account/network writes; preserve that contract. React Query counts are supplementary evidence, not the authority for readiness.

Include SDK activity initiated by reads/subscriptions, not only buttons that write app data: an authenticated read can acquire or refresh a session. Stopping the refresh timer does not freeze those callers. The operation inventory and exact-SDK experiment must prove no ungated participant can start another exchange after the quiet point. Otherwise signed-in refresh stays unavailable. This local font barrier is not a general queue durability repair: historical loading/persistence failure and ambiguous server outcomes retain their own S02 acceptance requirements.

On a confirmed Refresh press:

1. Synchronously enter preparation, close admission to new relevant operations and freeze UI actions/automatic dispatch. If any operation, blocker, recovery transfer or unknown participant already exists, abort preparation and restore ordinary operation immediately. Do not wait indefinitely for a request or cancel it to force eligibility.
2. Acquire a reversible queue pause covering foreground/reconnect/manual dispatch triggers. Require no running queue pass. Finish loading and serialize the newest queue snapshot through a **new explicit checkpoint API** that reports storage success/failure and a stable revision. The existing persistence chain catches errors, so awaiting its current promise cannot establish durability. Readback must strictly match the captured canonical owner-bound snapshot, not use the existing decoder's malformed-data-to-empty fallback. An empty checkpoint requires confirmed key absence; malformed/read-failed content is never evidence of an empty queue. The checkpoint revision covers enqueue, retry, dismissal, expiry and held-state changes. A failure leaves every RAM entry and normal recovery path intact and refuses reload.
3. Complete the signed-in Auth quiet point below and registered local persistence. Recheck account/session generation, route, active AppState, target scale, coordinator revision and queue revision after every await. Becoming background/inactive, a new callback, an unexpected Auth/account transition, navigation or data change before invocation invalidates the attempt. The expected same-owner TOKEN_REFRESHED from the preparation's own exchange is handled as specified below, rather than invalidating every successful attempt. Release pauses/admission on a pre-invocation failure. Never convert an uncertain outcome into a successful save.
4. Write and read back the minimal restart ticket below. Recheck the frozen snapshot synchronously, then invoke **public Expo `reloadAppAsync` exactly once** for that attempt. Do not navigate to Board first: it could erase the old route or mount a new generator before reload.
5. Invoking the native API is the irreversible boundary for this attempt. Keep writes paused until the new runtime boots. A returned promise, rejection or timeout does not prove that a native restart cannot still occur. Do not automatically reopen write actions or invoke reload again in that old runtime. If a new runtime does not arrive, explain how to fully stop and reopen Eiyu; simply going Home and returning may resume the same frozen runtime. Offer an App info link/instructions for Android Force stop if normal full closure does not restart it; never instruct clearing app storage or uninstalling. Durable queue state/ticket remain intact. This intentionally conservative failure case is a user-visible tradeoff for review. Before invocation, preparation can always fail/cancel and release its reversible pauses. No ticket or timer invokes reload on startup.

### Signed-in Auth quiet point and offline tradeoff

The current client has SDK-managed automatic token refresh outside React component state. Current [Supabase stop/start documentation](https://supabase.com/docs/reference/javascript/auth-stopautorefresh) describes timer lifecycle, not draining an already-running exchange. Installed source confirms that stopping clears timers; `getSession()` alone is not a universal drain because a refresh tick can start earlier than its expiry-margin check. Do not call private SDK fields/methods or add deprecated custom locking by assumption.

For this conservative first design, signed-in preparation uses public `stopAutoRefresh()` followed by public `refreshSession()` under the coordinator's own lease. This joins an existing exchange or completes a fresh one, then permits owner/expiry and existing SDK-storage completion checks. Only a same-owner successful result with sufficient lifetime for the bounded commit is accepted. The implementation must test this against the exact installed SDK's coalescing/storage behavior, including an exchange held before preparation; a mock returning success is insufficient. A rotation result is never logged, copied into a font ticket or treated as identity/guardian evidence.

The reviewed mobile resolution is Expo54.0.37/Router6.0.24 and supabase-js/auth-js2.112.4; this is source evidence, not the installed phone artifact's attestation. This SDK emits TOKEN_REFRESHED after saving and before resolving the refresh promise. Keep separate identity-transition and token-refresh revisions. While the preparation's owned refresh is active, a same-owner TOKEN_REFRESHED may be expected; validate its final result and rebase only that token revision after the await. Never rebase an intervening sign-out/sign-in, owner A→B→A, user/session replacement, incoming recovery or unrelated account change. Those invalidate the attempt even if the final UUID equals the original. If classification is ambiguous, refuse refresh. Do not call SDK methods or await the coordinator from the Auth event callback, which would create a callback/refresh wait cycle.

This adds an explicit preparation Auth refresh operation, subject to the SDK's normal request/retry behavior, and can require connectivity. It sends no AI call or verification email. **Signed-in font refresh is deferred offline or when session quietness cannot be established.** Ordinary offline quests and queued actions remain available, and no queue entry is removed to enable refresh. Blank signed-out login does not require a network refresh. This availability cost is explicit in the proposed design, rather than claiming safe offline session draining without evidence.

Use one mobile lifecycle owner for public stop/start calls so a foreground callback cannot restart the timer during preparation/commit. Restore the ordinary active/background lifecycle on pre-invocation cancellation/failure and on a completed new-runtime bootstrap. Do not asynchronously call SDK methods inside `onAuthStateChange`; record only an invalidating epoch there. Preparation has a ten-second maximum intent lifetime, and the last session result must have at least fifteen seconds of remaining validity at invocation; a changed clock or insufficient lifetime refuses refresh. A preparation deadline cancels the font intent, not the Auth exchange: its lease remains until the actual promise settles, with no fake completion or automatic retry. If these guarantees cannot be demonstrated without unsupported SDK behavior, keep signed-in refresh disabled and the font release gate open.

This is a local client barrier, not proof that old hosted/provider requests across other clients have drained. The separate S02 request-drain release gate remains open.

## Minimal route ticket and startup

Store one strict, versioned font-refresh ticket in its own AsyncStorage key. It contains only a random attempt identifier, creation/deadline timestamps (five-minute maximum validity), exact installed runtime/app variant, target font scale, captured owner UUID or signed-out sentinel, and an allowlisted destination. Owner UUID is an existing internal account reference, not new identity evidence. Never log the ticket or expand it to a navigation-state snapshot.

Allowed destinations are the actual **board, status, chain and gym** tabs, plus blank login. Optional view fields are closed enums only: Board lane and Status HERO/STATS/WEEKLY. Preserve them if supplied by the existing screen's coordinator participant. No quest/exercise IDs, raw URL/query/hash, account-overlay instruction, signup mode, recovery route, code, email, birthday or field value is allowed. Full back-stack/modal restoration is not promised. Selecting a destination never grants Auth or processing permission. A ticket restores display preference only; every data read/write rechecks current owner/permission. The UUID binding does not prove the same login session survived an entire process death or offline A→B→A sequence, so no stronger claim is made.

At every startup, initialize the coordinator before queue dispatch or automatic read-or-create work. Read the ticket, hydrate existing Auth and normal queue state, and wait for public navigation readiness. Consume/remove a valid ticket once before permitting restore; if removal fails, skip restoration and use normal initialization. A ticket never invokes reload at startup. Font-ticket I/O failure alone must not indefinitely lock the ordinary app; it forfeits font-specific route restoration and reports that limitation, while the existing queue/session initialization and their own safety rules still apply.

Restore the allowlisted tab/view only when variant/runtime, owner, deadline and current font scale match. A real incoming link/notification or account transition takes precedence: discard the ticket and let the existing receiving/Auth flow handle the event. Never persist incoming credentials to preserve a route. Invalid, stale, extra-field or wrong-owner tickets cannot navigate to another account's context; remove only the font key and use the normal safe destination. No cleanup clears Auth, queue, widget or tracker caches. Actual queue/session hydration failure retains its separate safety/recovery behavior; it is not repaired by dropping data.

Cached incoming events are a separate prerequisite. The current notification hook keeps its handled identifier/date only in a React ref, so an old native last-response value may replay after JS reload and wrongly override the tab ticket. Similarly, an already-consumed initial callback URI must not be confused with a newly delivered Auth link. Do not clear the native notification cache broadly at refresh commit, since that can erase a genuinely newer tap. Before enabling affected refresh paths, prove one-time handled-event consumption through supported SDK APIs with a concurrent-new-event test; if the old/new distinction cannot be proved without retaining raw URLs, tokens or secret digests, refuse that refresh path. No claim of callback/notification parity follows merely from the coordinator's RAM epoch. This review adds no persistence of notification contents or secret-bearing initial intents.

Gate queue dispatch and automatic generation until bootstrap/route selection is resolved, including paths mounted briefly by Router. Resume normal participants once, through their existing initialization/reconciliation paths. Preserve queue IDs, base counts, uncertainty, original account dates, expiry and explicit-Retry markers. Font refresh itself does not call Retry, `flush`/send for a held entry, manual Generate or a provider. Existing authorized Status automatic behavior after completed startup is unchanged; this work must not add a transient extra mount/inference.

Do not claim the coordinator can recover a callback arriving after native reload is already irreversible. That narrow handover needs explicit physical acceptance: incoming links must follow the existing fail-closed receiver and never switch the normal account or trigger an update on their own. A lost/expired recovery attempt may require reopening/requesting a link; no automatic credential replay is allowed. This residual cannot be hidden by storing a bearer URL. If a safe behavior cannot be demonstrated, keep the repair/release gate open.
