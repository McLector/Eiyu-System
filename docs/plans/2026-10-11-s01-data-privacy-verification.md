## Demonstrated ownership approach and its limits

Current [Supabase email link/OTP documentation](https://supabase.com/docs/guides/auth/passwordless-login/auth-email-otp) supports requesting proof with `signInWithOtp({email, options:{shouldCreateUser:false}})` and verifying `type:'email'` with an OTP or token hash. This can reauthenticate an existing auto-confirmed account without enabling login-blocking signup confirmation. Token/link verification returns Auth-validated account identity; the experiment also checked fresh `otp` AMR evidence.

Proposed S02 server flow:

1. Authenticate the existing quest session using server-owned Auth identity, resolve its current canonical email, and create a short-lived private challenge bound to account ID/current email/version, creation/expiry, attempts and consumed status. Clients cannot choose the identity or write proof. Apply server resend/attempt controls and generic delivery errors; do not expose account existence or generate new accounts.
2. Send a supported Supabase OTP/link to that resolved address. Keep the original quest session active. Prefer typed OTP for mobile; if links are also offered, use explicit web/Android handlers and tested allowlists. Do not put account sessions in callback URLs or logs. Do not depend on `resend(signup)` for already auto-confirmed legacy users.
3. Submit code/hash and opaque challenge ID to the authenticated backend. Use a separate nonpersistent Auth client to verify it, compare returned user ID and email with the challenge/requester, re-read current Auth email, and atomically commit proof only if the current email still matches. Reject another account's otherwise-valid proof. Consume once, handle failed DB persistence without silently treating the client as verified, discard temporary Auth session tokens and revoke them without revoking the original quest session where supported/tested.
4. Store proof in private server-owned storage tied to current identity/email version. Server eligibility rechecks current account/email, independently of stale JWT/user metadata. Gate both summary reads and every generation/quota path before spend; keep quest RPCs untouched. Session refresh and checking status only read authoritative eligibility.
